## 1. 项目定位

本项目（SmartCCTV）fork 自开源项目 **Video-analytics-pro**，目标是制作**自己的内网监控系统**。

## 2. 用户原始需求（原文复制）

> 本项目（SmartCCTV）fork自Video-analytics-pro
> 希望制作自己的内网监控系统
> 总体摄像头数量不是很多（<10），但是要智能，主要是人脸识别人脸库，联动控制门禁。人的行为识别风险预警等。
> cpu资源充足，希望不使用gpu
> 不需要rbac等权限管理系统，进入则可查看全部，但是需要totp密码
>
> 应该选择性优化，如yolo可以使用更高版本
> 内网域名定为"cctv.lobn"
> 如果需要后端，则技术栈使用uv+python3.14.x
> 需要启动脚本START.sh（交互式菜单），计划运行在内网单机debian(无GUI)上

### 需求要点拆解

| 维度 | 要求 |
|------|------|
| 规模 | 摄像头 < 10 路 |
| 智能 | ① 人脸识别 + 人脸库 + 门禁联动；② 人的行为识别与风险预警 |
| 算力 | CPU 充足，明确不用 GPU |
| 权限 | 无 RBAC；登录即可看全部；用 TOTP 密码做门禁 |

| 域名 | 内网域名 `cctv.lobn` |
| 后端技术栈 | uv + Python 3.14.x |
| 运维 | `START.sh` 交互式菜单；部署于内网单机 Debian（无 GUI） |

## 5. 明确排除 / 暂缓的事项

- 不做 RBAC、多用户、权限分级（用户明确不需要）。
- 首期不做 TLS（内网 HTTP）。
- 跌倒检测等基于姿态的行为识别列为**二期**（用 yolo26-pose 可实现，但首期先用检测+轨迹几何规则保证 CPU 与可靠性）。
- 活体/防照片冒充检测列为**可后加**（InsightFace 2.x 有 RGB liveness 插件可参考，见 04 文档）。
- 告警通道：Web 面板 + SSE + 浏览器通知；**v2 增加企业微信机器人推送**（需服务器出站访问 `qyapi.weixin.qq.com`，纯隔离内网不可用）。Telegram 等其它外部通道仍不采用。

## 9. 边界裁定与架构决策（v6，2026-11-24）

### 9.1 范围裁定（本项目 vs 未来项目）

- **本项目** = 内网监控 + 监控直接相关智能（YOLO 检测/规则告警/人脸识别，后期姿态）+ **门禁执行器**（仅作为"智能的执行末端"，控制平面最小化）+ **极简告警输出模块**（Gotify，1-2 天工作量）。
- **移出本项目** = 预约小程序（用户/订单/支付/时长卡，未来云端独立项目）、通知系统完整形态（多渠道路由/模板/分级/重试）、多门店管理/会员体系。
- 判断依据（用户原话要点）：监控的价值闭环是"**发现异常 → 有人知道**"，没有通知等于闭路摄像头；但通知无智能含量，不值得作为独立系统投入——降级为 MVP 内极简模块。

### 9.2 "分服务 vs 分机器"裁定（对评审意见的分析结论）

- **采纳**评审核心结论：按**服务**拆、不按**机器**拆；多台虚拟机在当前规模是过度设计。隔离的目的（故障隔离 + 资源隔离）由**容器 + cgroup 硬限制**即可满足，虚拟机只多出 N 倍系统运维。
- **再砍一刀**：评审给出的 4 容器 + EMQX 方案是"监控+门禁+预约全形态"的答案；本项目当前范围更小，落为**三段演进**——**阶段0（MVP）：单进程**（内部模块严格解耦 + 心跳看门狗 + 降级链，见 07 §17）→ **阶段1：Docker Compose 拆 door-gateway / vision / web 三容器**（触发器：预约系统上线，或门禁变 24×7 关键路径；总线升级轻量 mosquitto）→ **阶段2：分机器**（触发器：CPU 持续 >85% 且降频无效、摄像头 >8、或合规要求视频物理隔离）。
- **结构纪律**：MVP 起事件总线消息 schema 版本化、模块只走总线通信——拆容器是部署形态变化而非代码重写。
- GPU 注记：本项目明确不用 GPU；性能触顶优先降频/减路/换物理机。

### 9.3 控制平面 / 数据平面（四条规则）

1. 门禁执行器（控制平面）代码最小、可人工审计、极少更新；只消费事件，只做"验证+执行"。
2. 跨服务通信只走事件总线；禁止直调内部接口、禁止直写对方数据库。
3. **开门路径不经过 AI**：人脸开门 = vision 比对出结果 → 事件 → door 执行；AI 崩溃/升级时物理按钮与未来扫码照常。
4. **生物特征不出内网**：人脸库仅存本地（AES 落盘加密）；未来小程序录入人脸由云端仅转发图像、云不留存。

### 9.4 与预约小程序的关联（现在立契约、未来再实现）

- 预约小程序 = 云端独立项目，与监控**分开**——理由：不同信任域（公网 vs 内网）、不同生命周期（C 端迭代 vs 监控求稳）、不同数据（订单 vs 视频）。
- 连接：本地**主动外连**（MQTT over TLS 或 HTTPS webhook），**云零入站端口**；云下发"预约→开门授权"，本地上报"开门事件/扣时确认"（幂等 key 防重复扣时）。
- 门禁接口预留：door schema 版本化（v1: face_match/manual/button；v2 预留 token/qr 字段），签名密钥共享——现在只留字段，不实现 token 校验。
- 详细设计见 [07-架构设计细节.md](07-架构设计细节.md) §20。
