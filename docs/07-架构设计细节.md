# 07 · 架构设计细节（实施计划的补充展开）

> 本文是对 [06-实施方案-完整版.md](06-实施方案-完整版.md) 的细节补充：为什么这样设计、关键参数怎么取。均为设计推导，尚未实现。

## 1. 视频链路（核心设计）

### 1.1 每路摄像头两类 ffmpeg 子进程

| 进程 | 用途 | 关键参数 | 生命周期 |
|------|------|----------|----------|
| **分析进程**（所有摄像头） | RTSP → 解码帧 → Python | `-rtsp_transport tcp -i <substream> -f rawvideo -pix_fmt bgr24 -`（stdout 管道） | 守护：退出/无帧 N 秒自动重启；`-rw_timeout`/`-stimeout` 防挂起 |
| **连续录像进程**（仅门口） | RTSP → 直落盘 | `-c copy -f segment -segment_time 600 -reset_timestamps 1 door_YYYYmmdd_HHMM.mp4` | 同上；`-c copy` 不转码近零 CPU |

- 用**子码流**（substream，一般 704×480/720p H.264）做分析：解码便宜、YOLO26 640 输入本来就用不上 1080p；人脸摄像头如需更高分辨率可单独调子码流分辨率或用主码流抽帧。
- Python 侧"latest-frame 总线"：读线程从 stdout 持续读帧丢进 `{cam_id: latest_frame}`（只保留最新一帧 + 事件通知），分析线程按固定节奏（2-5fps）取最新帧——天然背压丢弃、不堆积。
- 帧尺寸核算：720p bgr24 ≈ 2.7MB/帧；分析 5fps × 8 路 ≈ 108MB/s 管道吞吐，本机内存带宽毫无压力。

### 1.2 播放：MJPEG（服务端画框）

- 沿用原仓库被验证的形态：`<img src="/api/cameras/{id}/mjpeg">`，`multipart/x-mixed-replace; boundary=frame`。
- 输出帧 = 最新分析帧 + 画上检测/人脸框（服务端画框，浏览器零逻辑）；JPEG 质量 ~70、缩放到显示宽；每路限 5-10fps 输出。
- 无人观看时降频/暂停编码（统计 img 标签在线连接数），省 CPU。
- 事件、统计、告警走 **SSE**（`/api/events`，EventSource），替代原 1s axios 轮询。

## 2. CPU 预算（8 路满配估算，供硬件核对）

| 项 | 估算 | 依据 |
|----|------|------|
| ffmpeg 解码 8 路子码流 | ~0.15 核 × 8 ≈ **1.2 核** | 720p H.264 软解经验值 |
| 门口连续录像 `-c copy` | ≈ 0 | 不转码 |
| YOLO26n @ 2fps × 8 路 | 8×2×39ms ≈ **0.65 核** | 官方 CPU ONNX 基准（torch 略慢但有富余） |
| 人脸（门口机 2fps：SCRFD 30ms + 1-2 张脸 ×10ms） | ≈ **0.1-0.2 核** | 估算 |
| MJPEG 编码（观看中的几路 ×5fps） | ≈ **0.1 核** | 720p JPEG ~3-5ms |
| **合计** | **≈ 2.2-2.5 核** | 现代 6 核+ CPU 富余；s 档模型或全 5fps 也能扛 |

## 3. 门禁子系统

### 3.1 硬件方案（推荐给"还没买"的用户）

- **HTTP 控制型网络继电器模块**（KMtruk/KMtronic、亿佰特等，局域网 GET/POST 触发，几十元级）。
- **接线**：继电器**常开（NO）触点并联到门禁面板"开门按钮"两端**——等效于替人按开门键：
  - 不改动原有门禁控制器逻辑（兼容任何电插锁/磁力锁系统）；
  - **fail-secure**：继电器断电即触点断开 → 门保持上锁；
  - 开门时长 = 触点吸合时长（可配置，默认 5s）。
- 可选：门磁接继电器板输入干接点，回读"门未关"状态并告警。
- 注意门口人脸摄像头安装位：室外机高度 1.4-1.6m、避免逆光；广角注意边缘人脸过小（SCRFD 640 检测小人脸能力有限）。

### 3.2 软件设计（`server/door.py`）

- `DoorAdapter` 抽象接口：`open(seconds)` / `state()`；实现 `HttpRelayAdapter`（配置 URL 模板），预留 `GpioAdapter`（gpiod）/`MqttAdapter`。
- 联动规则（门口摄像头 → door）：
  1. FaceDB 白名单命中：**余弦相似度 ≥ 阈值（初始 0.45，可调）且连续 ≥3 帧确认**（防单帧误识）；
  2. 冷却期（同一人 N 分钟内不重复开门，默认 2 分钟）；
  3. 可选时段限制（如夜间只有特定人员可开门）；
  4. 陌生人持续徘徊（门口区域出现同一 track ≥ 30s 且无匹配）→ 告警事件（不开门）；
  5. 每次动作写门禁日志（人员/陌生人、相似度、抓拍路径、时间）。
- Web 端提供手动开门按钮（登录态即可用）。

## 4. 数据库（SQLite，要点）

| 表 | 关键字段 |
|----|----------|
| persons | id, name, note, enabled, created_at |
| face_embeddings | person_id(FK), embedding(BLOB float32×512), source_snapshot_path |
| events | id, cam_id, type(zone_intrude/line_cross/loiter/crowd/face_known/face_unknown/door_open/…), payload(JSON), snapshot_path, clip_path?, ts |
| recordings | cam_id, path, start_ts, end_ts, kind(continuous/event) |
| door_logs | ts, person_id?, similarity?, action(open/denied/manual), snapshot_path |

- 事件去抖（同一规则同一 track 的重复告警间隔）在 rules.py 内存中处理，不依赖 DB。
- embedding 匹配 = 每人取多张注册照的均值/最大值比对（人数 <100 时暴力余弦即可，微秒级）。

## 5. 行为规则引擎（`server/rules.py`）

- 输入：每路的检测框 + ByteTrack track（id、bbox 历史、速度）+ 摄像头标定（区域多边形/越线线段，存 config，前端在快照上绘制）。
- 规则：
  - **区域入侵**：track 底边中点进入多边形（连续 ≥K 帧）；
  - **越线**：track 质心跨过有向线段（记录方向）；
  - **徘徊**：track 在区域内累计停留 ≥ T 秒（容忍短暂离开）；
  - **聚集**：区域内同时人数 ≥ N；
  - 布防计划（按时间段/立即/撤防），夜间自动切换更敏感阈值。
- 全部为纯函数几何计算 → pytest 可完整单测（不需要真视频）。

## 6. 认证（TOTP）

- 首次启动：生成 `secret` 存 config（0600），START.sh/终端打印 otpauth:// URI 与二维码（qrcode 库渲染 ASCII）；设置页可重置。
- 登录：`POST /api/auth/login {code}` → pyotp 校验（±1 窗口）→ itsdangerous 签名 Cookie（HttpOnly，有效期可配，默认 7 天）。
- 中间件：除 `/api/auth/*`、`/login`、静态登录页外全部要求会话；MJPEG `<img>` 同源自动带 Cookie（这就是弃用 token-in-URL 的原因）。
- 无 RBAC、无多用户（需求明确）。

## 7. 配置与运维

- `config.yaml`（含摄像头列表、ffmpeg 模板、规则、门禁、留存天数、TOTP secret 路径）；`.example` 入库、真实配置 gitignore。
- `START.sh` 交互菜单（bash；whiptail 可用则 whiptail，否则纯数字菜单）：
  `1) 安装/更新（uv sync + 下载模型 + 前端构建[如有 node，否则用预构建 dist]  2) 启动  3) 停止  4) 重启  5) 状态  6) 日志(tail)  7) 备份DB  8) 重置TOTP  9) 生成 systemd unit(可选开机自启)  0) 退出`
- 服务：`uv run uvicorn server.app:app --host 0.0.0.0 --port 8300`（nohup + pid 文件，或 systemd unit）；前端 dist 由 FastAPI StaticFiles 挂载，单端口出全部流量。
- `cctv.lobn`：内网 DNS 指向服务器 IP，或在各客户端 hosts 添加；服务本身不绑定域名。

## 8. 留存清理

- 定时（每小时）扫描 `recordings/`：连续录像保留 N 天（默认 14）、事件片段保留 M 天（默认 30），超期删除并清 recordings 表索引；磁盘水位保护（<5% 时按最老优先删）。
- 磁盘参考：门口 24/7 `-c copy` 2Mbps 子码流 ≈ 0.65GB/天/路（若录主码流 4Mbps ≈ 1.3GB/天）；事件片段每条 10-30MB。

## 9. 存储分层（本地热层 + 可选 S3 冷层）〔v2〕

- **原则**：SQLite 只存元数据与索引；大对象（录像/抓拍）永远在文件系统/S3。
- **默认内置 RustFS**（Apache-2.0，无 AGPL 顾虑）：CCTV 单机上以 Docker 跑单节点 `rustfs/rustfs`（S3 端口 9000 / 控制台 9001，data 目录挂 `data/s3/`），由 START.sh 菜单项或 systemd 管理。前端/后端统一走 **S3 标准协议**。
- **可选外置**：config 里配置 endpoint/access-key/secret-key/bucket，指向 RustFS 集群、MinIO 或任何 S3 兼容服务——代码零改动（协议可互换）。
- **分层策略**（config 可调）：
  - 热层（本地盘）：事件片段与抓拍保留 N 天（默认 7）；门口连续录像保留 M 天（默认 14）。
  - 冷层（S3，可选开启）：事件片段与重要抓拍按策略**上传 S3 后本地可删**（保留索引）；连续录像超期直接删或按容量上传。
  - 迁移任务：每小时定时扫描 + 磁盘水位保护（<5% 优先处理最老文件）。
- **回放**：`/api/recordings/{id}/stream` 由服务端判断本地/S3 流式回源（支持 HTTP Range，前端 `<video>` 拖动进度条可用）。
- **依赖最小化**：S3 客户端优先 botocore/aioboto3（或按需手写签名，避免重依赖）；若完全不启用 S3，则 storage.py 退化为纯本地文件管理，行为与 v1 一致。

## 10. 红外/夜视兼容 〔v2〕

- **现象**：红外模式（IR-CUT 滤片移除 + 850nm LED 补光）下画面为**灰度**；人脸有"红眼"式反光；近距离/反光物易过曝。纯软件无法控制 IR-CUT，但可感知并适配。
- **管线要求**：
  - 所有处理不假设彩色：读帧后统一 `if ndim==2: cvtColor(GRAY→BGR)` 或复制通道再入 YOLO/SCRFD（两模型对灰度输入均可用）；画框/JPEG 编码路径同样兼容。
  - **昼夜自动判定**：按帧平均亮度（或 IR 特征）滑动判定 day/night 状态，事件与日志带 `mode` 字段；状态切换产生系统事件。
- **每摄像头夜间档案（night_profile）**：分析 fps、规则阈值（夜间入侵/徘徊更敏感）、人脸匹配策略均可覆盖。
- **夜间人脸现实与对策**（ArcFace 在灰度/IR 上精度下降）：
  - 门口机默认策略（可配）：夜间匹配**阈值上调 + 连续帧数增加**；或降级为"仅记录+告警，开门需手动确认"；
  - 推荐硬件配合：门口补**可见光**照明（人脸识别友好），或把 IR LED 角度避开正对人脸、摄像头避免逆光与过曝区。
- 录像/检测不受夜视影响（IR 视频记录照常）；门禁日志标注夜间开门事件以便追溯。

## 11. 企业微信机器人通知 〔v2〕

- **依赖**：仅 httpx POST，不引入 SDK。webhook：`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<KEY>`（KEY 存 config，0600 权限）。
- **消息类型与限制**（官方口径）：
  - `text`：支持 `mentioned_list`/`mentioned_mobile_list`（@全体或指定手机号）；
  - `markdown`：富文本，但**不支持 @ 提醒**；
  - `image`：需先 `upload_media`（`.../upload_media?key=KEY&type=image`，multipart）取 `media_id`（3 天有效），仅 JPG/PNG、≤2MB；
  - **限流：每 webhook 20 条/分钟**（超限返回 `api freq out of limit`）。
- **可靠性设计**：内存 asyncio 队列 + 全局节流（默认 ≥3s/条）；失败指数退避重试；同群可挂多个机器人组成 webhook 池轮询（突破 20 条/分钟）。
- **事件映射**（config 分级 info/warning/critical，默认 warning 及以上推送）：
  - 门禁：已知人员开门（附抓拍图）/ 陌生人徘徊 / 手动开门 / 门未关 → 图片或 markdown；
  - 行为告警：入侵/越线/徘徊/聚集 → text/markdown + 可选抓拍；
  - 系统：服务重启/录像异常/磁盘水位 → 仅 critical。
- **前提**：服务器需出站 HTTPS 访问 `qyapi.weixin.qq.com`（443）——内网需放行或配置代理；纯物理隔离内网该通道不可用（此时仅剩面板 SSE/浏览器通知）。
- 每事件类型支持冷却（如陌生人告警 10 分钟内只推一次）与可选每日静默时段。

## 12. 长期运行与资源治理（防磁盘/内存溢出）〔v4〕

> 目标：7×24 无人值守。三原则：**所有无界增长点都有配额；所有失败都有降级路径；关键资源有硬闸。**

### 12.1 磁盘容量账本

- **可用池** = 磁盘总量 − 保留区（默认 20GB 与 10% 取大者），各类数据从池中分硬配额（config 可调，示意默认）：连续录像 50%、事件片段 15%、抓拍+缩略图 10%、S3 本地缓存/临时 10%、DB+备份+其它 15%。
- 清理器每小时按配额独立执行、先删最老，日志记录清理字节数；**内置 RustFS 的数据目录与本机共享磁盘，同样计入账本**（S3 不是免费空间！）。
- `diskmon` 状态机：OK → WARN(池<20%) → CRITICAL(池<5%)；CRITICAL 停新增录像、通知+事件；恢复后自动续录（滞回 5% 防阈值抖动）；状态进 health/面板/企业微信。
- 崩溃残留治理：启动与定时任务清理孤儿 ffmpeg（按 cmdline 匹配自有进程）、临时 seek 切片、上传 tmp。

### 12.2 内存账本

| 组件 | 量级 | 治理手段 |
|------|------|----------|
| YOLO26s + torch 运行时 | ~600MB RSS（含 torch 导入开销） | 单实例共享；`torch.set_num_threads` |
| SCRFD + ArcFace（onnxruntime） | ~200MB | 仅门口机启用，可配置关闭 |
| latest-frame | 每路 1 帧 × ~2.7MB(720p) | **单槽**：读线程覆盖写，禁多副本 |
| 每路 ffmpeg 进程 | 50-150MB × N | 进程数上限 = 路数×2 + 临时切片并发 ≤2 |
| 事件缩略图缓存 | LRU 上限 512MB | 超限逐出（落盘缓存为主） |
| embedding 矩阵 | 微小（<100 人） | 上限保护：>10 万条改磁盘搜索/分片（远期） |
| 各类队列（通知/检测/上传） | — | maxsize + 满则丢最旧并计数，指标进 health |
| **总硬闸** | — | systemd `MemoryMax=2G`（按机型调）+ Restart=on-failure |

- 泄漏防线：活跃 asyncio 任务数、子进程数、RSS 三指标进 health/面板，每日巡检与基线对比，漂移即告警。

### 12.3 数据库 / 日志 / 时间的长期治理

- SQLite：WAL + 定时 `PRAGMA wal_checkpoint(TRUNCATE)`；events/door_logs/detection_stats 超期归档（S3 或删除）；VACUUM 低频（维护菜单手动）。
- 日志：RotatingFileHandler 10MB×5；维护菜单"诊断包"打包（日志 + 脱敏 config + health 快照）。
- 时间：systemd-timesyncd/chrony 状态进 health（长时间漂移会打乱录像索引与事件顺序）。
- 每日巡检（内置调度或 cron）：`PRAGMA integrity_check` 快检、孤儿清理、配额报告 → 汇总事件（可选企业微信日报，一条 summary）。

## 13. START.sh 完整菜单设计〔v4〕

**架构**：菜单只是壳；检测/修复逻辑抽到 `scripts/lib/checks.sh` + `checks.py`，保证 `diagnose` 与 `repair` 行为一致、且可被 cron/CI 非交互调用。渲染：whiptail 可用则用，否则纯文本数字菜单；全局支持 `START.sh <子命令> [--yes/--ci]` 与 `--help`。

| 组 | 子项 | 内容要点 |
|----|------|----------|
| **1 环境检测** | diagnose | 逐项：uv/python 与 lock 一致性、ffmpeg、docker（可选）、glibc、磁盘/内存、qyapi 出站（通知可用性）、端口占用、数据目录权限、模型文件 SHA-256、DB 可打开 → OK/WARN/FAIL 分级报告 + 修复建议 |
| **2 环境修复** | repair [--yes] | 按检测结果生成修复动作（`uv sync`、下载缺失模型、建目录、修权限、重建 lock、修 DB 权限），**执行前逐条列出将运行的命令**；--yes 免确认 |
| **3 运行** | 3a 终端直跑 | `uv run uvicorn …`：start/stop/restart/status/logs，nohup + pid 文件 |
| | 3b Docker | `docker compose`（§14）：backend(host 网络) + 可选 rustfs；镜像构建/拉取 |
| | 3c systemd | 生成/移除 unit（专用非 root 用户、`MemoryMax`、Restart、自启开关）；status 显示进程/容器/unit 状态 + health 摘要 |
| | （互斥） | 三种运行模式共用同一数据目录，**切换/启动前自动检查其它模式未在运行** |
| **4 维护** | 4a 重建录像索引 | 断电/损坏自愈：扫描录像目录 ↔ DB 比对，补录缺失索引、清理孤儿索引 |
| | 4b 重置密钥 | TOTP 重置（轮换签名 secret → 踢全部会话、重打二维码）；门禁 KEY / S3 凭证重配向导 |
| | 4c 备份/恢复 | DB + config + 人脸库（排除录像）；可选加密（age）；恢复流程交互确认 |
| | 4d 清理/归档 | 手动触发清理器；查看配额账本用量；VACUUM；事件归档 S3 |
| | 4e 诊断包 | 日志 + 脱敏 config + health 快照打包 zip |
| **5 自动化测试** | test [--ci] | ruff + pytest（单元分层）+ smoke_test.sh（端到端 30s）；--ci 非交互输出 PASS/FAIL（§15） |
| **6 帮助/退出** | help | 用法 + 常见故障排查速查 |

- 首启引导：无 config 时进入交互式初始化问答（摄像头 URL/门禁/通知 webhook），并提示 root 降权（创建 smartcctv 用户）。

## 14. Docker 运行模式〔v4〕

- **compose 服务**：`smartcctv`（`network_mode: host`——RTSP 直连最省事、无端口映射坑；卷挂 config/data/models）+ `rustfs`（可选，桥接 9000/9001，卷 data/s3）。
- **镜像**：`python:3.14-slim` + uv（lock 分层安装，构建缓存友好）+ apt ffmpeg；多阶段构建；镜像内同用非 root 用户。
- **模式取舍**：终端直跑 = 默认（零额外依赖、资源无虚拟化损耗）；Docker = 追求依赖隔离/已有容器运维习惯时选；两者共用宿主数据目录（互斥运行）。
- 注意：host 网络下端口即宿主端口；若改桥接，需在摄像头/门禁设备侧放行容器网段。

## 15. 自动化测试策略〔v4〕

**分层**（`START.sh test` 一键执行 1+2）：

1. **单元层**（pytest，无重依赖、秒级）：规则几何（点在多边形/越线方向/徘徊计时边界）、face 余弦匹配与阈值、SCRFD 后处理（合成 anchor 用例）、config 加载与非法值、TOTP 窗口与防重放、通知模板渲染、清理器时间边界。固定 fixtures：样例帧、合成 anchor、规则场景。
2. **端到端冒烟**（`scripts/smoke_test.sh`，~1 分钟，无摄像头/无 GPU 可用）：起服务 → `/api/system/health` 全绿（无模型时用假模型跳过项）→ file 源跑 30s → 断言：检测事件入库、MJPEG 返回 200、SSE 收到事件 → PASS/FAIL。
3. **可选 CI**（.github/workflows）：ruff + pytest；torch 等重依赖不进 CI（smoke 由人工或自托管 runner 跑）。

## 16. 缓存策略与削峰填谷调度〔v5〕

### 16.1 三层缓存（整合 v3/v4 并补预热）

| 层 | 内容 | 预热（谷期执行） |
|----|------|------------------|
| 热（内存） | embedding 矩阵、latest-frame、分段时间索引、最近事件 N 条 | 启动即载入 embedding/分段时间索引 |
| 温（本地盘） | 事件缩略图、近期片段、统计聚合结果、时间轴索引 | 首页宫格缩略图、最近 24h 时间轴索引、当日统计缓存 |
| 冷（S3） | 归档事件、超期录像 | 不预热（按需 Range 回源） |

- 缓存穿透/雪崩：缩略图与统计生成**单飞合并**（同 key 并发请求只算一次）；缺缓存返回占位，不阻塞核心。
- 失效：事件写入时**只失效对应时间桶**（缩略图/统计/时间轴），不做全量失效。
- 前端：API 短 TTL + SSE 主动失效；Service Worker 壳缓存归 P2。

### 16.2 峰值计算与负载画像

- 采集：`stats.py` 每分钟采样（CPU、内存、各等级任务耗时、观看连接数、事件数）→ 内存环形缓冲 + 小时聚合落 `detection_stats`。
- **峰值三层含义**：
  1. **历史峰值**：昨日/本周峰值、95 分位——面板"负载曲线 + 峰值标注"（容量规划依据）；
  2. **预测峰值**：按小时聚合的历史中位/分位（+简单趋势）——供预调度（峰期前预热、重活避开）；
  3. **实时峰值保护**：当前 load gauge 触发削峰（见下）。
- 输出：报表页新增"负载与峰值"视图；周报 digest 附峰值时段。

### 16.3 削峰填谷调度器（`scheduler.py` + `jobs` 表）

- **谷期重活清单**（全部幂等、可中断续跑，存 `jobs` 表记录进度）：S3 归档上传、缩略图生成、时间轴索引重建、统计预聚合、DB checkpoint/VACUUM、备份、模型预热、日志轮转。
- **进入谷期条件**（可配）：时间窗口（默认 03:00-06:00）**或** 实时负载低于阈值（CPU<30% 持续 5 分钟）。
- **峰期让路**：load gauge 上升 → 立即挂起重活；分析资源倾斜门口机与活动路（与 09 B1 自适应降频共用同一 load gauge，单一信号源）。
- **互斥与限流**：重活全局并发上限（默认 2）；与清理器/diskmon 共用配额账本。
- 调度器自身是 P3 任务——它挂起不影响任何核心功能。

## 17. Web 与核心隔离：崩溃/高压力韧性 + 会话限制〔v5〕

### 17.1 隔离原则与降级链

- **核心管道与 Web 层解耦**：录像/检测/门禁/通知/diskmon 为 lifespan 启动的后台任务组，HTTP 层只读状态、下指令、推流。核心任务带**心跳看门狗**（无心跳 N 秒 → 记录并重启该任务；各任务独立重启，互不影响）。
- 默认**同进程 + 心跳看门狗**（简单可靠，8 路规模足够）；**预留拆进程方案**（core 无 HTTP 进程 + web 进程走 loopback）——明确不做默认，避免过度设计。
- **四级优先级降级链**（负载压力时自上而下牺牲）：
  - P0 不可降：录像写入、门禁指令、企业微信告警、磁盘临界处理；
  - P1 只降频：检测/人脸分析、事件入库；
  - P2 先降：MJPEG/SSE/搜索/报表（降帧率、限并发、拒绝新观看）；
  - P3 随时挂起：谷期重活。
- Web 崩溃（异常/被打满/被 kill）→ systemd 重启 Web 进程，核心不中断；核心异常被全局异常处理器兜底不崩进程。

### 17.2 会话与请求限制

| 项 | 默认 | 说明 |
|----|------|------|
| 并发会话上限 | 20 | 超出拒绝新登录（提示已达上限）；面板可看会话列表并踢除 |
| 单 IP 连接上限 | 5 | 防单点滥用；登录失败限速已有（09 C1#2） |
| 并发观看路数 | 4 | MJPEG 同时观看的上限，超出排队或提示 |
| 单路 fan-out | ≤3 | 超出走共享编码/降帧 |
| 慢客户端 | 输出缓冲上限 | 满即断流，绝不积压（防拖死编码器） |
| SSE | 心跳 15s + 积压上限 | 断线重连；积压超限丢最旧 |
| 请求限速 | 每 IP 10 req/s | 慢接口（搜索/报表）超时 + 转后台任务 |

- 压力自测：health 页含 Web 响应延迟指标；压测脚本（并发脚本/locust 可选）验证降级路径与核心不中断。

### 17.3 崩溃/压力演练清单

kill -9 Web 进程、填满并发连接、模拟慢客户端、长连接挂起、日志灌满磁盘——逐项验证：录像连续、门禁/告警不受阻、恢复后状态一致。（并入 09 的验证计划）

## 18. 网络异常韧性（少数卡顿/崩溃/无响应）〔v5〕

### 18.1 内网侧（RTSP/设备，细化 v3 A1）

- 区分**断流**（无帧）与**卡顿**（帧间隔变大/抖动）：按帧间隔均值与方差分级告警（warn：间隔>2×基准；critical：>10×或超时）。
- 链路质量指标（帧间隔分布、重连次数/小时）进 health 与面板；每路独立故障域（一路坏不影响它路）。

### 18.2 外网侧（企业微信/S3）——熔断 + 不丢

- **熔断器**：连续失败 N 次（默认 5）→ open（暂停发送 60s）→ 半开试探 1 条 → 恢复 close；避免网络抖动时的无效重试风暴。
- **通知不丢（磁盘溢写）**：内存队列满时溢写 SQLite/append-only 文件；网络恢复后**补发**——策略可配：critical 事件必补发；普通事件超龄（默认 >2h）丢弃，防恢复瞬间轰炸。
- S3 上传同理：失败退避 + 熔断 + 源文件确认前不删（v3 已述，统一到同一熔断组件）。
- DNS/NTP：qyapi 解析失败退避重试；NTP 失步告警（v4 已有）。
- health 页增两项：外网连通性（qyapi/S3）、内网链路延迟矩阵。

## 19. 企业微信通知矩阵升级〔v5〕〔v6 裁定：MVP 降级为极简告警输出（Gotify 默认 + 企业微信可选），本章完整形态移出本项目，留作未来通知系统参考，见 §20.5〕

> 注意：群机器人是**单向推送**（不能接收指令）——"获取统计信息"落地为**定时/事件触发的主动推送**（digest），按需查询仍在 Web 面板。

### 19.1 通知矩阵（五类 × 等级 × 策略）

| 类别 | 触发项 | 默认等级 | 策略 |
|------|--------|----------|------|
| 检测告警（已有） | 入侵/越线/徘徊/聚集/画面异常/断流 | warning-critical | 冷却 + 同类聚合 |
| **门禁**（新增细化） | 已知人员开门（附抓拍+姓名）/ 陌生人徘徊 / 手动开门 / 开门失败或结果未知 / 门未关 / 夜间开门 | info-warning | 开门类即时推送 |
| **人脸库**（新增·审计） | 人员录入/修改/删除、批量注册完成、抓拍注册成功、疑似重复人员 | info | 审计式推送（谁在何时改了库，防"被偷偷录入"）；先落 audit 表再发送 |
| **统计**（新增·digest） | 日报：当日人数/事件/告警摘要 + 峰值时段；周报：趋势 + 磁盘配额报告 | info | **定时 digest**（谷期调度器触发），markdown 表格 |
| 系统（已有，细化） | 服务重启/崩溃恢复/录像异常/磁盘水位/模型加载失败/KEY 失效/大量失败登录 | critical-warning | 即时 |

### 19.2 设置与实现

- 前端"通知设置"页：每类开关 + 等级过滤 + 独立冷却/聚合窗口 + 每日静默时段 + digest 调度配置（时间/频率/内容勾选）+ 测试发送按钮。
- 实现：`notify/` 扩展为通知中心——事件总线订阅 → 矩阵规则匹配 → 模板渲染 → 分级队列 → 限流/熔断（§18）→ webhook；digest 由调度器（§16）触发，从 `detection_stats`/`events` 聚合生成 markdown。
- 审计保证：人脸库变更类通知**先落库再发送**，发送失败不丢审计记录。

## 20. 系统拓扑与服务拆分（v6）

> 本章回应"监控/门禁/通知要不要分开、要不要多台虚拟机、与预约小程序如何关联"三个问题，并裁定外部评审意见（"按服务拆、不按机器拆"）在本项目当前阶段的落地形态。

### 20.1 边界裁定（本项目 vs 未来项目）

```
┌─────────────── 本项目（内网监控 + 监控智能）───────────────┐
│  视频接入 → YOLO检测 → 规则告警(越线/入侵/徘徊)              │
│         → 人脸识别(识别/陌生人判定)     ← 监控直接相关智能    │
│         → [后期] 姿态/动作识别                               │
│              ↓                                              │
│         事件总线 ←── 门禁执行器（只作为"智能的执行末端"保留）  │
│              ↓                                              │
│         极简告警输出（Gotify推送，1-2天工作量）               │
└────────────────────────────────────────────────────────────┘

┌─────── 明确移出本项目范围 ───────┐
│  预约小程序（用户/订单/支付/时长卡）│ ← 未来独立项目（云端）
│  通知系统的完整形态               │ ← 多渠道路由/模板/分级/重试
│  多门店管理、会员体系             │
└──────────────────────────────────┘
```

### 20.2 按服务拆、不按机器拆——演进路径

外部评审的结论（"按服务分开、不该按机器分开，容器+cgroup 已同时提供故障与资源隔离，虚拟机在本规模无回报"）**采纳**；但其 6 容器 + EMQX 方案是"全形态"答案。本项目当前范围更小，落为**三段演进**：

| 阶段 | 形态 | 触发条件 | 隔离手段 |
|------|------|----------|----------|
| **0（MVP，当前默认）** | 单进程 FastAPI：内部模块严格解耦 + 心跳看门狗 + 四级降级链（§17） | <10 路、门禁仅执行末端、无预约系统 | 任务级隔离 |
| **1（容器拆分）** | Docker Compose 三容器：`door-gateway`(0.5c/256M，最高优先) + `vision`(4-5c/6G) + `web`(0.5c/512M)；内部总线升级 MQTT（8 路规模优先 **mosquitto** 轻量版，EMQX 等未来云桥接再上）；可加 Gotify 容器 | 预约系统上线；或门禁变为 24×7 关键路径（需独立升级/重启） | cgroup 硬限制 |
| **2（分机器）** | vision 移第二台物理机；录像转 NAS（合规场景） | CPU 持续 >85% 且无法降频解决；摄像头 >8；合规要求视频物理隔离 | 物理隔离 |

**关键结构纪律（现在就要立）**：单进程内部已按模块 + 事件总线解耦（`events.py` 至今的设计），**拆容器是部署形态变化，不是代码重写**——因此总线消息 schema 从 MVP 起就版本化、字段只增不改。GPU 注记：本项目明确不用 GPU；性能触顶时优先降频/减路/换物理机，GPU 仅作远期可选（与需求约束冲突，默认不考虑）。

### 20.3 控制平面 / 数据平面（沿用外部评审规则，明确为四条）

1. **door-gateway = 控制平面**：代码最小、可人工审计、极少更新、restart:always；只消费事件，只做"验证+执行"。
2. **跨服务通信只走事件总线**（进程内 bus 或 MQTT）：禁止直调内部接口、禁止直写对方数据库。
3. **开门路径不经过 AI**：人脸开门 = vision 比对出结果 → 事件 → door 执行，二者无同步依赖；AI 崩溃/升级/重启时，物理按钮与（未来）扫码开门照常。
4. **生物特征不出内网**：人脸库仅存本地（AES 落盘加密）；未来小程序"录入人脸"由云端仅转发图像到本地、云不留存。

### 20.4 与预约小程序的关联契约（现在立契约、未来再实现）

- 定位：预约小程序 = **云端独立项目**（C 端：微信登录、开门、录入人脸、时长卡/支付），与监控系统**分开**——不同信任域（公网 vs 内网）、不同生命周期（C 端快速迭代 vs 监控求稳）、不同数据（订单 vs 视频）。分开的理由不是技术而是**边界**：内网系统不应为 C 端迭代与攻击面买单。
- 连接方式：**本地主动外连、云零入站端口**——MQTT over TLS（阶段1 后）或 HTTPS webhook（MVP 期即可）推云；方向：云下发"预约→开门授权"，本地上报"开门事件/扣时确认"（幂等 key 防重复扣时）。
- 门禁接口预留：door 指令/事件 schema 从 MVP 起版本化（v1：face_match / manual / button；v2 预留 token / qr 字段）；本地与云共享签名密钥（或非对称验签）——**现在只留字段与文档，不实现 token 校验**。
- 数据边界表：云 = 用户/订单/时长卡/审计日志；本地 = 人脸库/录像/门禁日志；人脸图像流仅"云转发→本地入库"，云端不落人脸。
- 未来人脸录入流：小程序拍照 → 云端转发 → 本地录入接口（内网直连或反代）→ 本地入库。

### 20.5 通知降级（v6 裁定）

- MVP 只做**极简告警输出模块**（1-2 天）：事件 → 级别过滤（默认 warning+）→ 去重/冷却 → **Gotify**（自托管、内网可达、默认）→ 企业微信 webhook（可选第二通道，复用 v2 适配器）。
- 判断依据：监控的价值闭环是"**发现异常 → 有人知道**"，没有通知的监控等于闭路摄像头；但通知本身无智能含量，不值得独立投入。
- **§11/§19 的完整通知形态（矩阵/digest/审计推送/设置页）从 MVP 移出**，归"通知系统完整形态"（未来项目/后期），本章保留作参考文档。

### 20.6 运维补充（按需裁剪）

- edge-agent/远程通道：单机家用可先不做（可选：自托管反向隧道+心跳）；日志轮转与每日巡检已有（§12）。
- 门禁事件日志：本项目默认无限期保留（≥6 个月要求自然满足）；云端审计库等预约系统上线再说。
